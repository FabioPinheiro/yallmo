Problem

The selected-tool interface leaks availability knowledge into startup, where a Coach-specific supplement duplicates knowledge used by lazy resolution.

Solution

Deepen the existing selected-tool module so it owns declaration availability across both validation timings, without adding a catalog framework or changing trusted wiring semantics.

  • Locality: catalog knowledge stays together
  • Leverage: both callers share rules
  • Depth: less caller coordination
  • Tests exercise the configured interface

Evidence & deletion test

  • ServerApplication:180–187 explicitly appends Coach declarations before validating all configured agents.
  • ToolWiringResolver:49–58 validates final output IDs alongside base IDs, including later additions.
  • Deleting the resolver would redistribute real validation complexity; keep and deepen it. Delete duplicated caller knowledge, not its guarantees.
  • Shared tools, Coach-private functions and Folder's empty selection are real variation; they do not justify a new resolver adapter.

Interface is the test surface

  • Keep ToolWiringSuite:123–177: trusted additions and local IDs.
  • Keep ServerApplicationSuite:479–519: unavailable IDs fail before storage opens.
  • Keep ServerSubmissionSuite:117–163: selected private functions reach inspection.
  • Add paired configured-path checks: private explicit IDs succeed; unknown IDs fail before storage. Test invocation and managed execution with the same selected definitions.
Decision guardrail. docs/SERVICE_TOOLS_WIRING.md, docs/Capabilities_Architecture.md and docs/AGENT_TOOL_WIRING_PLAN.md explicitly retain eager validation. Preserve it, including unselected-agent failures. Preserve filter-before-wiring, trusted additions, the skill-reader exception, lazy generation caching and lower-level guards. Deferring all checks or imposing a general post-wiring filter would reopen those decisions and is not this recommendation.
Evidence limit: the generic resolver accepts later local IDs, while startup only supplements Coach. A non-Coach configured-path failure is inferred from source, not a reproduced defect; do not invent a new agent kind merely to justify the refactor. First exploration: establish the smallest deletion of duplicated catalog knowledge that preserves today's two validation timings. No new adapter seam is needed.

Problem

Prompt acceptance's interface includes a caller-managed read/check/write order, with the expected-head decision outside the module that appends the prompt.

Solution

If a permitted concurrent mutation can interleave, deepen acceptance in the existing persistence-owning module while retaining configured admission, continuation policy and application lifetime where they are.

  • Locality: head checks meet mutation
  • Leverage: both storage adapters agree
  • Depth: fewer ordering facts escape
  • Tests cross the acceptance seam

Evidence & deletion test

  • ServerExecutionService:98–121 loads history, checks the head, updates continuation exclusions and then submits.
  • OrchestratorLive:46–51 separately validates the agent, adds membership and appends the prompt.
  • Deleting configured execution would scatter Busy admission, detached waits and sanitized outcomes; the module earns its keep.
  • The existing storage seam has two real adapters: in-memory and filesystem. No new admission adapter is justified.

Interface is the test surface

  • Existing ServerSubmissionSuite:373–433 checks Busy, independent-session overlap and stale expected heads.
  • :452–529 checks lost waits; :666–695 checks a closed application lifetime.
  • First establish a permitted competing head mutation and suspend deterministically between check and append.
  • Only if reachable, test the acceptance outcome through the same interface with both storage adapters; retain typed-failure versus unknown-outcome behavior.
Not a confirmed race. No competing remote mutation path was established in this review. The configured session gate may already exclude all relevant standalone callers. If so, stop: documenting the ordering contract is preferable to introducing a hypothetical seam.
Decision guardrail: preserve docs/SERVICE_WIRING.md: orchestration owns persistence; the runner owns decisions and action checks; branches never publish sessions; invocation is not a loop; caller disconnect does not cancel admitted work. No global inference lock, replay registry or exactly-once guarantee. A deeper acceptance module would not turn tool execution into a transaction.
