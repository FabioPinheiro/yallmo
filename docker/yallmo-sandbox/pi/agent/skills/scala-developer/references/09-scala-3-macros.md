# Scala 3 Macros and Compile-Time Derivation

Use this reference when designing, implementing, reviewing, or debugging Scala 3 inline code, quoted macros, reflection, `derives` methods, `Mirror`-based derivation, match types, or `Dynamic`/`Selectable` APIs backed by macros.

## 1. Start with the simplest mechanism

Macros increase compile-time cost, error-surface area, IDE complexity, and maintenance burden. Prefer the least powerful feature that preserves the required static guarantee.

| Need | Prefer |
| --- | --- |
| A generic operation parameterized by a type | ordinary generic method / type class |
| Different code for a literal argument | `inline`, `inline if`, `scala.compiletime` |
| Product/sum traversal with no syntax inspection | `Mirror`, tuple recursion, type classes |
| Case class can opt into generated behavior | `derives` and a `derived` method |
| Inspect field names, annotations, symbols, or arbitrary types | quoted macro + reflection |
| Generate a compile-time error tailored to source structure | quoted macro + `report.errorAndAbort` |
| Runtime JSON/schema validation | ordinary runtime code; optionally generated by a macro |

Use a macro only when ordinary polymorphism, `Mirror`, match types, or a manual type-class instance cannot express the contract clearly.

## 2. Mental model: two stages

A Scala 3 macro has two separate execution stages:

1. **Macro expansion / compilation time:** Scala compiles the caller, executes the macro implementation, and produces typed Scala code.
2. **Application runtime:** the produced code runs later in the application.

Keep the stages explicit in names and comments. A value of `Expr[A]` is *code that will evaluate to `A` later*, not an `A` available while the macro runs.

```scala
import scala.quoted.*

inline def twice(inline value: Int): Int =
  ${ twiceImpl('value) }

def twiceImpl(value: Expr[Int])(using Quotes): Expr[Int] =
  // Runs during compilation.
  '{ $value + $value } // Produces code that runs at application runtime.
```

At a call site `twice(21)` expands approximately to `21 + 21`.

### Quotes and splices

| Syntax | Stage meaning |
| --- | --- |
| `'{ code }` | quote: construct an `Expr[...]` representing `code` |
| `${ implementation(...) }` | splice: run macro implementation and insert its returned code |
| `$expr` inside `'{ ... }` | splice an existing `Expr` into newly quoted code |
| `'value` | quote/reference an inline method parameter as an `Expr` |
| `Expr(value)` | lift a known compile-time value, such as a `String`, into quoted code |
| `Type[T]` | evidence that lets macro code inspect/reify `T` |

The quote/splice nesting rules are strict. When code becomes hard to stage, split it into small helpers returning `Expr[A]` and document which stage each helper belongs to.

## 3. Standard macro shape

Put the inline public entry point and implementation in an object. The implementation must be statically accessible to the compiler at the macro call site.

```scala
import scala.quoted.*

object Example:
  inline def make[T]: Result[T] =
    ${ makeImpl[T] }

  // Public because the compiler invokes it from the separately compiled caller.
  def makeImpl[T: Type](using Quotes): Expr[Result[T]] =
    '{ new Result[T] { /* generated runtime implementation */ } }
```

Important rules:

- A macro implementation is normally `def impl[T: Type](...)(using Quotes): Expr[Result]`.
- A macro cannot normally be invoked from the same source compilation unit in which it is defined. Place macro implementation code in `main`; use it from a separately compiled module or test source.
- Do not hide a macro implementation behind a non-static class instance or a private accessor that callers cannot access; Scala reports that it is not statically accessible.
- The public inline method should have a stable, intentional return type. Macros are implementation details; callers should not need to know quotation APIs.
- Keep macro dependencies small. Do not perform file I/O, network I/O, time-dependent work, or environment-dependent behavior during expansion.

## 4. Literal arguments and `inline`

An `inline` parameter is substituted at the call site and can be inspected by a macro.

```scala
inline def route(inline key: String): Route =
  ${ routeImpl('key) }

def routeImpl(key: Expr[String])(using Quotes): Expr[Route] =
  val literal = key.valueOrAbort // compile error unless key is known at compile time
  // inspect literal
  ???
```

`valueOrAbort` is appropriate only when the API requires a literal. It intentionally rejects:

```scala
val dynamicKey = readFromConfig()
route(dynamicKey) // rejected by valueOrAbort
```

Document that restriction. If runtime values must work, use an ordinary runtime map/lookup instead of a macro.

## 5. Type-class derivation with `derives`

For a case class to opt into generated behavior, derive a **type class**, not a runtime value that needs request data.

```scala
trait Schema[A]:
  def decode(input: Input): Either[String, Output[A]]

object Schema:
  inline def derived[A]: Schema[A] = ${ derivedImpl[A] }

  def derivedImpl[A: Type](using Quotes): Expr[Schema[A]] =
    // inspect A and generate a Schema[A]
    ???

final case class Questions(worker: ChoiceQuestion, urgency: ScoreQuestion)
    derives Schema
```

`derives Schema` makes the compiler look for `Schema.derived[Questions]` and places the resulting given in `Questions`' companion. It is then available through ordinary implicit search:

```scala
val schema = summon[Schema[Questions]]
```

Good derivation design:

- Make the type class describe static capability or a reusable algorithm.
- Put runtime inputs in methods such as `decode(response)`.
- Make the generated instance validate assumptions before exposing an unsafe or narrowly typed view.
- Keep the generated API understandable without seeing macro internals.
- State exactly what `derived` accepts and rejects.

## 6. `Mirror` first; reflection when names or symbols matter

For products/sums, `scala.deriving.Mirror` can traverse element types without reflection. It is often sufficient for codecs, equality, rendering, or recursive type-class derivation.

```scala
import scala.deriving.Mirror

inline def derived[A](using Mirror.Of[A]): TypeClass[A] =
  // use product/sum mirror and tuple recursion
  ???
```

Use `quotes.reflect` when the macro needs data `Mirror` does not conveniently expose, such as:

- source-level field names;
- annotations;
- symbol flags;
- concrete member types resolved in the enclosing type;
- custom compiler diagnostics; or
- generated code tailored to a particular declaration.

### Common reflection operations

```scala
import scala.quoted.*

def inspect[A: Type](using Quotes): Unit =
  import quotes.reflect.*

  val tpe: TypeRepr = TypeRepr.of[A]
  val symbol: Symbol = tpe.typeSymbol
  val fields: List[Symbol] = symbol.caseFields

  fields.foreach { field =>
    val resolvedFieldType: TypeRepr = tpe.memberType(field).dealias
    val fieldName: String = field.name

    val isCaseClass = symbol.flags.is(Flags.Case)
    val isExpected = resolvedFieldType <:< TypeRepr.of[Expected]
    // `show` is useful in diagnostics, not as a semantic identifier.
    val readable = resolvedFieldType.show
  }
```

Use these operations deliberately:

- `TypeRepr.of[A]`: reflected type representation for `A`.
- `typeSymbol`: declaration symbol of a type.
- `caseFields`: constructor fields of a case class.
- `memberType(field)`: field type resolved in the context of the enclosing type; use it rather than a raw symbol type for generic classes.
- `dealias`: follows aliases before a subtype comparison.
- `<:<`: subtype test. Prefer it to comparing rendered type strings.
- `Flags.Case`: verifies the schema is a case class.
- `report.errorAndAbort(message)`: produce a source-positioned compile error and stop expansion.

Never make correctness decisions from `TypeRepr.show`, class names, or other display strings.

## 7. Generate runtime validation, not unjustified casts

Macros often know the *expected* shape at compile time, but external data is still untrusted at runtime. Generate checks before exposing a refined API.

```scala
trait AnswerSchema[Q]:
  def decode(response: Response): Either[String, AnswerView[Q]]
```

A derivation macro can inspect `Q`, then generate runtime checks for each required answer key and subtype. Only after all checks pass should it construct a typed view.

This is especially important when generated code contains `asInstanceOf`. A cast may be acceptable only when all of these are true:

1. a macro verifies the static schema;
2. a runtime validator verifies data from the external service;
3. the unsafe operation is hidden behind the validator's successful result; and
4. tests cover missing and mismatched external values.

If these conditions are not met, return an ADT or `Either` instead of casting.

### Building a list of generated checks

A useful pattern is to generate many small expressions and combine them:

```scala
def checkOne(response: Expr[Response], field: String)(using Quotes): Expr[Option[String]] =
  val fieldExpr = Expr(field)
  '{
    $response.values.get($fieldExpr) match
      case Some(_) => None
      case None    => Some("missing field '" + $fieldExpr + "'")
  }

val checks: List[Expr[Option[String]]] = /* one per reflected field */
val generatedList: Expr[List[Option[String]]] = Expr.ofList(checks)

'{
  $generatedList.collectFirst { case Some(error) => error } match
    case Some(error) => Left(error)
    case None        => Right(...)
}
```

The macro-time `List[Expr[Option[String]]]` is not the same object as the runtime `List[Option[String]]` produced by `Expr.ofList`.

## 8. Typed dynamic field selection

An API can use `scala.Dynamic` plus a transparent inline macro to offer typed field syntax from a case-class schema:

```scala
import scala.language.dynamics
import scala.quoted.*

final class AnswerView[Q](...) extends Dynamic:
  transparent inline def selectDynamic(inline field: String) =
    ${ selectImpl[Q]('this, 'field) }
```

At `answers.worker`, the macro can:

1. require `"worker"` to be a literal with `valueOrAbort`;
2. find `worker` in `Q`'s case fields;
3. inspect its question type; and
4. emit an expression with the matching static answer type.

`transparent inline` is important: it lets the call site retain the emitted subtype, such as `ChoiceAnswer`, rather than only the common supertype.

Use this pattern sparingly:

- `Dynamic` requires `import scala.language.dynamics` at its definition.
- Unknown member syntax is less discoverable than normal methods; document examples and diagnostics clearly.
- It cannot type arbitrary runtime strings; provide a normal runtime lookup API for that need.
- Generated code runs at the caller's access scope. Any helper it calls must be accessible there, often public.
- Do not offer this view before schema/data validation succeeds.

`scala.Selectable` supports structural selection in other situations, but it does not by itself provide arbitrary unknown-member syntax. Use `Dynamic` only when the DSL benefit justifies it.

## 9. Types macros do and do not generate

Macros generate typed **terms/code**. They are excellent at generating a type-class instance, validation code, a codec, or a method body tailored to a known type.

Do not assume a macro can conveniently create a new stable public nominal case-class type with arbitrary named fields for every `Q`. In many designs, one of these is clearer:

- a type class with generated behavior (`Schema[Q]`);
- a typed wrapper `View[Q]` plus transparent inline accessors;
- match types and tuples for purely type-level mappings; or
- an explicitly declared response case class when it is part of the public domain model.

Keep the wire model separate from the ergonomic typed façade. External protocols commonly use maps or JSON objects; an internal schema can compile to and validate that representation.

## 10. Error reporting

A macro's error messages are part of its API. Fail early and name the offending declaration, field, type, and rule.

```scala
report.errorAndAbort(
  s"${field.name} in ${schemaType.show} has type ${fieldType.show}; expected Choice, Score, or Noul"
)
```

Good diagnostics answer:

- where is the error?
- what was found?
- what was expected?
- how should the developer fix it?

Do not turn configuration/schema mistakes into obscure generated-code errors or a later `ClassCastException`.

## 11. Testing macros

Test both compile-time and runtime behavior.

### Positive compile-time tests

Compile normal fixtures that demonstrate the intended inferred types:

```scala
val answers = request.answers(response).fold(fail, identity)
val worker: ChoiceAnswer = answers.worker
```

The explicit type annotation ensures a regression in macro expansion fails compilation.

### Runtime tests

For externally supplied data, test at least:

- valid response with every answer subtype;
- missing required answer;
- answer with the wrong subtype;
- malformed JSON when applicable;
- optional fields and provider extensions;
- wire round-trip when codecs are involved.

### Negative compile-time tests

Where the test framework supports compilation tests, assert that invalid schemas fail to compile: non-case-class `Q`, unsupported field types, unknown dynamic selections, and non-literal fields when literals are required. Keep the expected diagnostic stable enough to identify the rule, not every compiler wording detail.

Macros must be compiled before their use. A common layout is macro definitions under `src/main` and macro-use tests under `src/test`; the separate main/test compilation phases satisfy staging.

## 12. Review checklist

Before accepting Scala 3 macro code, verify:

- [ ] A simpler `inline`, `Mirror`, type-class, or runtime solution was considered.
- [ ] Public API has normal Scala types; quotes/reflection do not leak to callers.
- [ ] Stage boundaries are documented: what runs during compilation versus runtime.
- [ ] Macro entry point is `inline`; implementation is statically accessible in an object.
- [ ] Literal-only arguments are explicitly marked `inline` and documented.
- [ ] Reflection checks actual symbols/types (`memberType`, `dealias`, `<:<`), not display strings.
- [ ] Accepted shapes and rejected shapes have explicit diagnostics.
- [ ] Generated code validates untrusted runtime data before unsafe casts/refined views.
- [ ] Generated code can access every helper it references from the caller's package/module.
- [ ] Compile-time fixtures prove inferred types; runtime tests cover valid and invalid data.
- [ ] Compile-time work is deterministic, bounded, and free of I/O and secrets.
- [ ] The macro's generated behavior and compatibility expectations are documented.
