# Yallmo glossary

Use these definitions consistently when working on Yallmo. They describe the project's intended concepts, which may differ from how other AI harnesses use the same terms. They are not a claim that every described behavior is already implemented.

Profiles and memory are planned concepts, not implemented features at the time these definitions were established. Keep that distinction explicit when discussing current capabilities. Revisit their status when implementation is confirmed.

## Agent

An **agent** is a process that follows a specific program. Here, process means programmed behavior, not necessarily an operating-system process or an autonomous model-driven loop.

The program encompasses the behavior currently expressed through agent instances and runner logic. These are implementation components of agent execution, not definitions of separate kinds of agent. The exact boundary between agent-specific behavior and shared execution machinery still needs refinement; this glossary does not prescribe a one-to-one mapping to current classes.

What distinguishes an agent is the program it follows, rather than a persona, specialization, or collection of tools. Different agents may use different providers, profiles, tools, and skills, but those configuration differences alone do not define a different agent. Some agent programs may only work with certain providers; this does not transfer model-communication responsibilities out of the provider.

Normal end-user use centers on **one working agent with a small set of profiles**, rather than a catalog of role-specific agents. This does not exclude a separate human-input agent. Examples of distinct programs include:

- A transcriber that converts audio into text.
- A human-input agent whose only behavior is to let a human send a message. An agent does not have to perform inference or act autonomously.

The human-input agent is the conceptual role through which a human contributes messages. This is not a claim that current registered human authors already have executable agent implementations.

Users can switch agents at any point in a conversation; the agent is not fixed for the conversation's lifetime.

**Current direction, open to revision:** Instructions come from the agent, not the profile.

## Profile — planned

A **profile** is a switchable configuration that defines the tools and skills available to an agent for a particular working role.

Examples include:

- **Review:** tools and skills suited to reviewing code.
- **Implementation:** tools and skills suited to implementing changes.
- **Research:** tools and skills suited to gathering and investigating information.

Profiles let users work with the same agent in different ways without changing its underlying program. Users can switch profiles at any point within the same conversation, without switching agents.

Yallmo is intended to have a small, purposeful set of profiles, not a large catalog of specialized agents. Do not call each profile a separate agent.

Under the current direction, a profile selects tools and skills rather than supplying its own instructions. Skills may themselves contain guidance.

**Planned configuration direction:** Move the capability selections currently held in agent configuration into profiles. Profiles may have different levels: a general profile can provide a baseline, and an agent can add or remove tools relative to that baseline. The representation of those levels and the precedence/merge rules are not yet defined. A profile must not be assumed to be an immutable permission ceiling under this proposal; the relationship to non-overridable host restrictions remains to be designed.

A profile is not an account, credential set, or login configuration. Credentials are handled by the provider.

## Tool

A **tool** is an extension of the AI harness that groups related executable capabilities the model can use. A tool exposes one or more callable functions.

Examples include:

- Accessing external capabilities through UTPC or MCP.
- Reading files.
- Navigating the web.
- **Scalamode:** executing Scala code generated by the model, with the flexibility to perform operations permitted by its execution environment.

The planned profile configuration, together with any agent-level adjustments, determines which tools are available to the agent. Tools can bring their own skills to explain their use; an explicit tool-to-skill packaging relationship is an intended capability, not an implemented relationship in the current tool contracts.

The agent's program and its available tools are distinct: the program defines the process; tools provide capabilities that process can use.

Do not treat the flexibility of Scalamode as proof of unrestricted execution or OS-level sandboxing. Consult the implementation and execution-boundary documentation for actual permissions, restrictions, and isolation guarantees.

## Function

A **function** is one callable operation exposed by a tool. It has a name, an input schema, and an executable implementation.

For example, the `filesystem` tool exposes the `readFile` and `listFiles` functions. A tool may expose only one function, as with `scalamode`; this does not make the two concepts interchangeable.

A function definition describes the operation; the implementation performs it. Availability and authorization are separate from description: declaring a function does not install its implementation or grant permission to execute it.

### Function call

A **function call** is one invocation of a function, identified by a call ID and supplied arguments. A model can propose a call; trusted harness code validates, authorizes, and executes it, then records the corresponding result.

## Skill

A **skill** is a package of guidance or knowledge made available to an agent.

Skills are broader than procedural instructions. They can also serve as domain knowledge stores and project artifacts, containing:

- Task procedures and tool-usage guidance.
- Domain information and the current state of work in that domain.
- Domain records, such as conversations with a client or email records.
- Architecture Decision Records (ADRs).
- Specifications.
- Project definitions, terminology, and glossaries.

Calling a skill a database is an analogy for a place to keep domain information, not a requirement for a database engine, query language, or transactional semantics. The knowledge is not inherently immutable: it can be modified as the domain and its records evolve.

**Current implementation boundary:** Skills are read-only startup snapshots in the running application. Updating files does not refresh the loaded catalog until restart. An in-application write/refresh lifecycle remains to be designed; conceptual mutability does not imply that this lifecycle already exists.

Tools can bring their own skills as intended composition, and planned profiles define skill availability. Exact layered selection rules remain open.

This glossary is itself a skill: it records the meaning of project terms rather than providing an executable capability.

## Provider

A **provider** is the abstraction layer that handles communication between Yallmo and a model, whether through a remote API or a locally running model.

It is responsible for model-communication concerns, including:

- Preparing and sending the conversation in the format expected by the model's API or local runtime.
- Performing calls and handling responses.
- Handling credentials and authentication.
- Handling retries and failures.
- Recording communication logs.
- Hiding model-specific communication details from the rest of Yallmo.

Here, **conversation handling** means handling how the conversation is communicated to the model. It does not mean owning Yallmo's conversation history or storage.

The provider is Yallmo's integration component, not the external company or service supplying a model. A model and the provider used to communicate with it are distinct concepts; backend compatibility may constrain which provider an agent can use.

Today, provider-related responsibilities are distributed across adapters, mappers, clients, and authentication components. Treat these collectively as the current provider subsystem. The architectural goal is a coherent abstraction layer that hides those details from the rest of Yallmo, not necessarily a single implementation class. Future code should move toward this definition rather than redefine providers around the current class split.

Yallmo's long-term direction favors local and open-source models that users can control and run themselves. Providers also support access to remote models, including those available through subscriptions.

## Memory — planned

**Memory** is a mechanism for bringing information relevant to the conversation into its context when needed.

Possible approaches include:

- **Retrieval-augmented generation (RAG):** retrieving and injecting information based on its relevance or similarity to the conversation.
- **System-1 models:** deciding when information should be injected into the context.
- A combination of these approaches.

A skill packages guidance or knowledge; memory selects and brings relevant information into the conversation context.

The information sources, persistence behavior, and whether skills can act as memory sources remain undefined. Do not assume that memory automatically learns from conversations or writes information back into skills.

## Usage boundaries

- Do not use **agent** and **profile** interchangeably.
- Distinguish **tools** (capability groups), **functions** (callable operations), and **skills** (guidance/knowledge packages).
- Distinguish the **provider's communication and credential responsibilities** from conversation ownership and storage; profiles do not contain credentials.
- Include human-input agents without assuming every agent uses a model or acts autonomously.
- Keep planned **profiles**, their layering rules, and **memory** separate from verified implementation behavior.
- Distinguish modifiable skill knowledge from the current immutable runtime snapshot.
- Preserve open decisions as open decisions rather than silently turning them into requirements.
